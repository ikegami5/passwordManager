# PasswordManager

Scala / ScalaFXで作られた、ローカルで動作するパスワード生成用GUIアプリです。
サービスごとの生成条件とsaltを保存し、入力したマスターパスワードからパスワードを再生成してクリップボードへコピーします。

## このリポジトリの扱い

別プロジェクトへの移行を予定しており、ここでは既存の動作と互換性の維持、検証、移行に必要な情報の記録を行います。
依存関係のバージョンアップ、機能追加、メインロジックの変更は予定していません。
AIエージェントによる作業時は[AGENTS.md](AGENTS.md)を参照してください。

## ビルド・起動

ロジックのビルド・テスト用に、WSL内に**OpenJDK 11（JDK、11.0.x）とsbt 1.4.9**を用意してください。ユーザーが導入済みです。
JDKのバージョン指定はリポジトリにありませんが、既存のScala / JavaFXに合わせてJDK 11を選びます。確認したJava / javacは11.0.32.1、sbtは1.4.9です。
[Scala公式のJDK対応表](https://docs.scala-lang.org/overviews/jdk-compatibility/overview.html)も参照してください。
Scala 2.12.13とJavaFXの依存ライブラリはsbtが取得するため、別途ScalaやシステムのOpenJFXをインストールする必要はありません。
今後のテスト対象はメインロジックとし、GUI操作、画面表示、クリップボードのテストは不要です。
生成処理と改行処理はGUIから分離し、GUIとテストから同じ実装を呼び出します。
アプリを手動起動する場合には、別途JavaFXとAWTを利用できるGUI・クリップボード環境、必要なネイティブライブラリが必要です。
初回ビルドではsbt本体、プラグイン、ライブラリの取得にネットワーク接続が必要になります。
不足するソフトやライブラリのインストール、設定変更は、ユーザーに確認してから行ってください。

リポジトリ直下で実行します。

```bash
java -version
sbt 'show sbtVersion'
sbt compile
sbt test
sbt assembly
```

`sbt test`は`src/test/scala/passwordManagerMain/CompatibilityTest.scala`の検証を実行します。
テストフレームワークの追加依存はなく、別JVMで`java.awt.headless=true`を指定して逐次実行します。不一致があれば非ゼロで終了します。
さらに、`build.sbt`の`test in assembly := {}`により、`sbt assembly`はテストを実行しません。

生成したJARの起動コマンドは次のとおりです。先に下記の隔離テスト手順を確認してください。

```bash
java -jar PasswordManager.jar
```

`start.sh`は`/bin/zsh`を要求し、スクリプトのあるディレクトリへ移動してJARをバックグラウンド起動します。
WSLのbashでは上記の直接起動コマンドを利用できます。表示されるエラーを確認できるよう、テスト時はフォアグラウンドで起動します。

## 保存データと互換性

- 保存先は**プロセスのカレントディレクトリ**の`./data.txt`です。JARの配置先からは決まりません。
- ファイルはUTF-8の平文で、1行が1サービスです。マスターパスワードや生成パスワード自体を保存する処理はありませんが、サービス情報とsalt履歴を含む重要なデータです。
- `data.txt`とJARはGit管理対象外です。実データ、実マスターパスワード、実生成パスワードをGit、ログ、文書、テストfixtureへ含めないでください。
- サービス登録と「パスワード変更」でファイル全体が即時上書きされます。複数プロセスによる同時利用を想定した排他処理はありません。
- `data.txt`が開けなければ空ファイルの作成を試みます。行の解析に失敗するとエラー表示後に一覧を空として扱うため、実データで試さず、元ファイルをアプリ停止中にバックアップしてください。

保存行のフィールド順は次のとおりです。標準的なCSVの引用符処理はありません。

```text
serviceName, serviceInfo, passwordHasCapital, passwordHasNumeral, symbolsInPassword, lengthOfPassword, oldestSalt, ..., newestSalt
```

読み込み時はコンマで分割して各フィールドを`trim`します。コンマは`\C`、サービス情報内の改行は`\n`、記号欄のスペースは`\S`として保存します。
saltはファイルでは古い順、実行時のリストでは逆順で、インデックス0が現在のsaltです。
「パスワード変更」はsaltの追加であり、以前のsaltも残ります。サービス名・説明は生成用のハッシュ入力に含まれません。

互換性確認時は特に次の挙動を維持します。

- マスターパスワードの受付条件は半角英数字8文字以上。生成文字には必ず小文字を含め、設定に応じて大文字・数字・指定記号も含めます。
- 登録時の長さは4以上を受け付け、保存時に64以下へ丸めます。記号は登録時の`toSet.toList`による順序を含めて保存され、保存された文字順も生成結果に影響します。
- SHA-512を64回適用します。saltを後ろ、前の順で交互に付加し、各回の出力を512文字の二進数文字列として次の入力へ渡します。文字列からバイト列への変換は引数なしの`getBytes`です。
- 最終ハッシュの部分文字列、seed、Scalaの`Random.setSeed` / `Random.shuffle`、文字集合の順序によって生成文字列が決まります。候補はseed加算0〜100の101通りで、条件を満たさない場合は生成エラーになります。
- タイマーは30から毎秒カウントし、0を表示した次の処理でクリップボードを空にします。終了時にも空にします。タイマーは途中で別途コピーした内容も上書きします。

生成処理やデータ形式の詳細は、推測による再実装ではなく現行ソースを基準にしてください。

## 新プロジェクトへの移行メモ：短すぎるパスワード

- 現行GUIは4文字以上を受け付けますが、短いパスワードでは小文字・大文字・数字・記号の必須条件を満たしにくく、101候補を探索しても生成できない場合があります。長さ4・大文字と数字必須・多数の記号を指定した固定入力で、この生成失敗をテストで確認済みです。
- 新プロジェクトでは**生成条件に応じた最小文字数の制限を設け、短すぎる長さを生成前に拒否する**こと。具体的な下限は移行先で決定し、境界値と生成失敗のテストを用意してください。
- 必須の文字種数以上の長さがあるだけでは、現行の有限候補探索での生成成功は保証されません。下限の設定だけで問題が完全に解消すると扱わず、候補が尽きた場合の処理も設計してください。
- この改善は新プロジェクトで行います。既存データの長さや現行の生成結果は、互換性維持のため自動変更しません。

## ロジックの互換性テスト

ユーザーの方針により、GUIのテストは行わず、メインロジックの検証で十分とします。
生成結果、保存行の解析・復元、salt履歴を主な対象にします。画面表示、ボタン操作、ダイアログ、クリップボード、タイマーの検証は必須項目にしません。
ファイルを扱うテストは`mktemp -d`などで作る合成データ専用の一時ディレクトリで実行し、実データの`data.txt`は読み書きしません。

`src/test/resources/compatibility/`に、ユーザーが現行GUIから採取した67件の保存行・最新saltでの出力・テスト専用マスターパスワードを配置しています。
元データは機密情報を含まないと明示されたものです。見出しと空行を除去し、改行をLFに統一していますが、値は訂正していません。
期待値は再生成して更新せず、手動採取データと一致しない場合は確認が必要な失敗として残します。

GUIの`password()`は`PasswordGenerator.generate`へ処理を委譲します。SHA-512、文字列処理、共有Random、候補探索、例外の計算処理は元ソースから移動しています。
`Record`はGUIアプリの代わりに`LineSeparators`を参照し、アプリ側の既存改行メソッドも同じ処理へ委譲します。
`Records`の一覧管理・ファイルI/Oと、UI内の入力チェックは今回のテスト対象外です。テストは実データもクリップボードも読み書きしません。

SDKMANで導入したsbtが非対話シェルのPATHにない場合は、今回確認した配置先から実行できます。

```bash
/home/impor/.sdkman/candidates/sbt/1.4.9/bin/sbt test
```

検証項目は次のとおりです。

1. GUI採取の67件について出力が完全一致すること。逆順で再実行し、他のサービスの生成を挟んでも一致すること。
2. salt追加後も以前のsaltから同じ基準値を再生成でき、保存・読み込みで履歴順序が維持されること。
3. 大文字・数字の有無、記号（スペース、コンマ、正規表現の特殊文字を含む）、長さ4・64などによる生成結果と生成失敗を確認すること。
4. サービス情報のコンマ・改行、記号欄のスペース、空フィールド、trimなどの保存形式と復元結果を確認すること。
5. 登録時の長さの上限64への丸め、salt生成・追加を確認すること。UI内だけにある入力チェックやエラー表示の操作テストは対象外とすること。

過去saltは再現性を確認しますが、過去saltのGUI採取出力は未提供のため、GUIとの出力一致は未検証です。

固定入力の例（実データではありません）：

```text
compat-example, synthetic fixture, true, true, !@#, 16, 0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz01
```

この1行をテスト用`data.txt`へ保存し、合成マスターパスワード`CompatTest123`で基準値を採取できます。
この説明用の1行はGUI採取の67件とは別で、期待出力を持ちません。移行先との比較では採取済みの固定行を再登録せずそのまま読み込み、saltと記号順を維持してください。
基準値と採取環境を記録してから移行先と比較します。正常動作しない箇所は、互換性の基準となる既存挙動と改善要望を区別して記録してください。
